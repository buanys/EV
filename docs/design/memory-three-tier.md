## 0. 一句话

- **L1 是草稿本**：系统自己记，模型看不见细节、也改不了，只知道有这么个东西。
- **L2 是模型的记事本**：跨会话永久，没有容量上限，模型用工具增/删/改。
- **L3 是常驻上下文**：8000 中文字符，从 L2 里挑出来的那些，每轮都在提示词里。

## 1. 目标与非目标

**目标**

- 跨会话记住稳定事实，而不是把整段聊天塞进上下文。
- 全链路可追踪：L2 的任意一条能回到 L1 的原话与时间。
- 提炼失败可恢复：不重复提炼，也不丢一段对话。

**非目标（v1）**

- 向量检索 / embedding。
- 跨设备同步。
- 改动内核（`core`/`loader`）。全部在插件层与 `agent-api` 契约层完成。

## 2. 分层

| 层 | 名字 | 内容 | 模型能否读写 | 进上下文 | 容量 |
|---|---|---|---|---|---|
| L0 | 会话历史 | 对话原文（现有 `MemoryService`） | 只读（按轮裁剪） | 是 | 按轮裁剪 |
| L1 | 草稿本 | 对话与工具调用的原始记录 | **不可见、不可改** | 否 | 滚动保留 |
| L2 | 记事本 | 精炼条目，跨会话永久 | **可增 / 可改 / 可删** | 否，按需检索 | **不限** |
| L3 | 常驻区 | 从 L2 挑出来置顶的条目 | 通过 `pin` / `unpin` 选择 | **是** | 8000 中文字符 |

L1 与 L0 的区别：L0 是模型看得到的对话上下文；L1 是系统侧的完整底稿（含工具调用、结果、
被裁剪掉的部分），只用于提炼与追溯，不进入模型视野。

## 3. 各层结构

### L1 — 草稿本（系统侧）

```
id           l1_000123
sessionId    会话 id
seq          会话内消息序号（单调递增，幂等游标用）
at           时间戳
actor        user | assistant | tool | system
text         原文（工具调用记工具名 + 参数摘要 + 结果摘要）
refs         [L0 消息 id]
```

- **模型不可见**：任何工具都不返回 L1 正文，只有 L2 条目的 `sources` 里能看到 id。
- **模型不可改**：没有修改接口。
- **模型知道它存在**：system prompt 里一句话说明（见 §6），作用类似于「你有潜意识，
  但读不到它，需要的话用 `recall` 查记事本」。

### L2 — 记事本（模型侧）

```
id           m_000123
kind         preference | fact | task | convention
title        ≤40 字
body         正文（可长，建议 ≤500 字，不强制）
keywords     3–8 个检索词（可空）
sources      [l1_...]        ← 追溯链，提炼产生的条目必填；模型手写的可为空
sessions     [sess_...]
status       active | superseded | archived
supersedes   m_000101        ← 冲突时指向被替代的条目
impact       1.0             ← 模型可调，L3 排序用
origin       model | distilled
createdAt / updatedAt
```

**没有容量上限**。条目多靠索引与检索解决，不靠删除解决。

**权限边界**：

- `origin = model` 的条目：模型可以改、可以删；提炼流程**只读**，不修改。
- `origin = distilled` 的条目：提炼流程维护；模型可以改（改完 `origin` 转 `model`），
  因为模型比提炼更清楚上下文。

### L3 — 常驻区

L3 不是独立的文本存储，而是 **L2 条目中 `pinned = true` 的那部分**的渲染结果。

```
L2 条目上增加：
pinned     true / false
pinOrder   排序权重
```

渲染时：

```
【关于用户】
偏好回答先给结论，不要结尾总结          ← m_000123 的 title/body 摘要
习惯用中文，少用列表                   ← m_000087

【环境】
插件目录 /sdcard/EV/mods               ← m_000201
```

- **预算只算渲染出来的正文**，条目的 `src` 不进提示词、不占字符。
- 8000 字符是硬上限；超了按「槽位权重 × impact × 最近使用」决定谁留在窗口里，
  被挤出去的只是不显示，条目本身仍在 L2（`pinned` 不改）。
- 单条超长时截断渲染，并记录「这条被截断过」，避免用户以为原文就这么短。

## 4. 提炼（L1 → L2）

### 4.1 触发

**且**条件：

1. 当前会话空闲 ≥ 15 分钟（没有在跑的一轮、没有待审批、没有未发送的草稿）；
2. 距上次覆盖点 ≥ 20 条消息（用户与模型的发言都计入）。

检查时机**不依赖后台定时器**（Android 会掐后台进程）：在应用回到前台、新消息发出、
本轮结束时各检查一次，满足就地异步执行。

### 4.2 两阶段状态机

```
开始前：写  pending(id, sessionId, fromSeq, toSeq, startedAt)
完成后：写  done(id, coveredUpTo = toSeq)，该批次产出的 L2 条目转为可见
```

- `pending` 存在且 `now - startedAt > 超时阈值` → 判为**中断**；
- 中断批次：**整批作废**（按 `batchId` 删除未转正的条目），下次重做这一段；
- 不做续写：半批数据的 `sources` 链不完整，比没有更糟。

### 4.3 幂等

覆盖范围用**消息序号**：本次提炼处理 `(coveredUpTo, lastSeq]`。

- `coveredUpTo` 没推进 → 可重做；
- 推进了 → 绝不会重复提炼。

「20 条」只是触发阈值，不参与边界计算。

### 4.4 提炼模型

独立配置项：**对话模型 / 提炼模型**。默认用更便宜的那个。

输入：L1 的 `(coveredUpTo, lastSeq]` + 现有 L2 的标题列表（用于去重）。
输出：若干 L2 条目，`origin = distilled`，必须带 `sources`。

与模型手写条目的关系：提炼**不覆盖** `origin = model` 的条目；撞车时新增一条并在
`sources` 里同时挂旧的，由模型自己决定是否合并。

## 5. 检索

L2 不进上下文，靠工具按需查：

```
recall(query, limit)  → [{id, title, kind, updatedAt}]
read_memory(id)       → 完整 body + sources
```

**索引方案（v1）：中文 bigram 倒排。**

- 正文切成双字词（「用户偏好简洁」→ 用户 / 户偏 / 偏好 / 好简 / 简洁）；
- 维护 `term → [L2 id]` 映射，查询同样切词后取交集；
- 不依赖分词器、不依赖 SQLite FTS（Android 自带的 `unicode61` 对中文无效）；
- 体量：几千条条目下内存索引足够，落盘为 JSON。

## 6. 提示词里的样子

L3 渲染后放进 system prompt 的**稳定前缀**（`identity` 之后、工具说明之前），
不放 volatile 尾部——L3 不随轮变化，放进 volatile 会让缓存每轮失效。

```
（identity 层）

你有记忆：L1 是系统自动记录的底稿，你读不到、也改不了；L2 是你的记事本，
可以用 recall 检索、用 remember 写入；L3 是当前常驻在你上下文里的部分（节省篇幅，只放了要点）。

【关于用户】
…

【环境】
…

【进行中】
…
```

模型对 L1 的「知道」就是这一行说明，不暴露任何正文。

## 7. 工具面

| 工具 | 作用 | 作用于 |
|---|---|---|
| `remember(text, kind)` | 新建一条记事 | L2（`origin = model`） |
| `update_memory(id, ...)` | 修改标题/正文/关键词 | L2 |
| `delete_memory(id)` | 归档（不物理删除，保留追溯） | L2 |
| `recall(query, limit)` | 检索，返回摘要 | L2 |
| `read_memory(id)` | 读全文 + 来源 | L2 |
| `pin(id)` / `unpin(id)` | 加入 / 移出常驻区 | L2 条目的 `pinned` |

全部**非 dangerous**：只改插件自己的数据区。

`delete_memory` 是归档不是物理删除，因为 L2 条目的 `sources` 指向 L1，而 L1 可能还被
别的条目引用；真要物理删除走 UI 的「清理」。

## 8. 与现有契约的关系

- `MemoryService`（`agent/memory`）保持原样，继续负责 L0 会话历史；本文不改它的签名。
- 新增 `MemoryStoreService`（key 建议 `agent/memory-store`），负责 L1/L2/L3 与提炼。
- 新增契约全部放进 `agent-api`，带默认值、不加枚举值（避免已编译的 `when` 崩溃）。
- 实现放在 `agent-memory` 插件内（它已经持有 `UserDataStorage`），不新建插件。

## 9. 分阶段

**M1（先能用）**：L2 + `remember` / `recall` / `read_memory` + bigram 索引 + L3 的
`pin` 与渲染。
验证一个前提：**模型到底会不会主动记**。若它从不调用 `remember`，后面都是空转。

**M2（自动）**：L1 落盘、提炼流程、两阶段状态机。

**M3（体验）**：记忆页 UI、去重合并、冲突提示。
