## 二、模块结构

```
third_party/cordis/        vendor 的内核（core、loader），固定版本，只读
host-api/                  契约：接口、数据类型、版本号。无实现，无 Android 依赖
host-core/                 宿主策略核心：清单解析、状态机、准入、登记、恢复。纯 Kotlin，JVM 可测
host-android/              适配层：安装、存储、组件、界面。只实现 host-core 定义的端口
host-runtime/              装配入口：把 host-core 与 host-android 接起来，宿主 App 只依赖它
plugins/base-*/            基础插件
plugins/feature-*/         功能插件
plugins/resource-*/        资源插件
plugins/integration-*/     集成插件
```

依赖方向只允许以下几种，其余一律由构建检查拒绝：

- `host-core` → `host-api`、`third_party/cordis`
- `host-android` → `host-core`、`host-api`
- `host-runtime` → `host-core`、`host-android`、`host-api`
- `plugins/*` → `host-api`
- 任何模块不得依赖 `host-runtime`
- `plugins/*` 不得依赖 `host-core`、`host-android`、`host-runtime`、`third_party/cordis` 中的非契约类型

## 三、宿主六个职责的边界

每个职责对应一个包，只通过端口与其他职责通信。

**入口**（`host.entry`）
- 只负责引导页和插件管理页的展示与触发。
- 不持有业务状态，所有数据从机制和裁决层读取。
- 入口只依赖机制中的"查询"与"触发停止安全模式"两个接口，不依赖其他部分。

**机制**（`host.mechanism`）
- 装配、生命周期、依赖解析、循环检测、替换、隔离执行选择、降级传播。
- 所有生命周期操作最终调用内核的 Fiber 与 LIFO 撤销，不自行实现清理。

**裁决**（`host.arbiter`）
- 信任判定、权限授权与撤销、启用停用卸载许可、数据去留规则。
- 裁决是唯一能把插件状态从"已校验"推进到"已准入"的地方。

**登记**（`host.registry`）
- 服务表（服务 id → 提供者、版本）、页面表（页面 id → 入口）、主题引用表。
- 只查表、只检查唯一性，不理解内容。

**恢复**（`host.recovery`）
- 失败计分、自动隔离、回滚、崩溃记录、安全模式的入口。
- 恢复只调用机制的停止接口和裁决的隔离接口，自己不停止任何插件。

**装配**（`host.compose`）
- 启动时决定加载哪些插件、顺序如何，并把清单表交给机制。
- 装配只决定顺序，是否真正运行由机制的激活阶段决定。

## 四、状态表

十个状态：

| 状态 | 含义 |
|---|---|
| 已发现 | 包已在私有目录，尚未读取清单 |
| 已校验 | 清单通过第 12 节校验，包哈希已记录 |
| 已准入 | 裁决通过：档位确定，高风险权限已同意（如需要） |
| 加载中 | 类加载器已创建，入口类已实例化，`apply` 执行中 |
| 运行中 | 所有 `inject` 服务就绪，服务与页面已登记 |
| 已降级 | 运行中，但某个可选依赖缺失或某个降级项已关闭 |
| 停止中 | 已收到停止指令，内核正在按 LIFO 撤销 |
| 已停止 | 撤销完成，资源已释放，可再次准入 |
| 失败 | 某一步出错，附原因码，未运行 |
| 已隔离 | 失败计分超阈值，阻止自动再启动，只能由用户手动恢复 |

**合法转换（其余一律拒绝并记录）：**

| 从 | 到 | 条件 |
|---|---|---|
| 已发现 | 已校验 | 清单与包校验全部通过 |
| 已发现 | 失败 | 任一校验失败，原因码写入记录 |
| 已校验 | 已准入 | 信任判定为可信或受限，且高风险权限已同意或无需同意 |
| 已校验 | 失败 | 信任判定为不可信，或用户拒绝高风险权限 |
| 已准入 | 加载中 | 机制开始激活 |
| 加载中 | 运行中 | `apply` 完成，所有 `inject` 服务就绪 |
| 加载中 | 已降级 | `apply` 完成，可选依赖缺失，且缺失的依赖在 `degradable` 中有对应项 |
| 加载中 | 失败 | `apply` 抛异常，或注册了清单之外的服务，或必需依赖缺失 |
| 运行中 | 已降级 | 可选依赖消失，或某降级项被关闭 |
| 已降级 | 运行中 | 依赖恢复，或降级项重新开启 |
| 运行中 / 已降级 | 停止中 | 用户停止、宿主停止、依赖的必需提供者被停止 |
| 停止中 | 已停止 | 内核撤销完成 |
| 停止中 | 失败 | 撤销过程中有 effect 清理失败（内核会阻止自动重新激活） |
| 运行中 / 已降级 / 加载中 | 失败 | 崩溃或超时，且未超阈值 |
| 失败 | 已隔离 | 失败计分超阈值 |
| 已停止 / 失败 | 已准入 | 用户手动重新启用（不是自动重试） |
| 已隔离 | 已准入 | 仅由用户手动解除隔离 |

**注意：**
- "失败"之后不会自动重试。重启进程不会把失败插件重新激活。
- 从运行中到失败，必须先经过停止中的清理，不能直接跳到已停止，以保证副作用被撤销。

运行中、已降级、加载中 → 失败：进入失败前必须完成 effect 撤销，撤销结果写入失败记录。

## 五、加载流程（实现规则）

启动时按以下顺序执行，每一步有明确的负责方。

1. **发现**：扫描私有插件目录，读取包列表。宿主负责。
2. **复制与校验**：若来自投放目录，先复制进私有目录，再对副本计算 SHA-256 并设为只读，之后只使用副本。宿主负责。
3. **清单与格式校验**：按清单规范第 12 节逐步校验。失败则进入"失败"。宿主负责。
4. **信任判定**：可信、受限、不可信。不可信直接失败，不进入后续。宿主裁决负责。
5. **准入**：检查权限声明，高风险权限未同意则不准入。宿主裁决负责。
6. **装配**：对所有已准入插件做依赖图检查，拒绝循环依赖，决定激活顺序。宿主机制负责。
7. **加载**：可信插件创建 `DexClassLoader`（Android）或 `URLClassLoader`（JVM），插件类优先，共享包走宿主。实例化入口类，调用 `apply`。内核 loader 执行。
8. **激活**：等待 `inject` 声明的服务就绪。服务就绪则进入运行中；必需依赖缺失则保持加载中直到超时，超时进入失败；可选依赖缺失则进入已降级。内核 Fiber 执行，宿主定义超时值。
9. **登记**：服务、页面、主题登记到登记表。登记冲突则失败。宿主登记负责。

**受限档位插件的加载**：步骤 7 改为在独立进程中加载，宿主通过 broker 转发调用。该部分在 Android 上的实现方式未确定，见第十一节未实测项。

## 六、运行时权限检查

- 所有插件可访问的宿主接口，都必须经过一道权限门，入口在 `host-api` 的调用签名处统一拦截。
- 默认拒绝：插件未声明、或声明后未获授权的权限，调用返回拒绝，不抛异常到插件外。
- 每一次拒绝和每一次高风险调用（`SHELL`、`CREDENTIAL_READ`、`FILE_WRITE`）写入审计记录，包括插件 id、包哈希、权限名、时间。
- 权限的授予和撤销只能由裁决层执行，插件不能请求自我授权。

## 七、失败计分与恢复

- 受限档位和可信档位插件都计分，计分规则相同。
- 每次崩溃计 1 分，每次超时计 1 分。超时阈值为宿主配置项，不硬编码。
- 计分在滑动窗口内统计，窗口长度为宿主配置项。
- 超过阈值，插件转入"已隔离"，并阻止自动重新准入。
- 失败记录保存：包哈希、失败步骤、原因码、时间、插件版本、撤销结果。
- 安全模式：启动时若检测到上次异常退出，进入安全模式，不激活任何非内置插件，只展示插件管理页。
- 回滚：替换插件失败时，回到上一个可用版本。上一个版本的包哈希必须仍在私有目录中，否则回滚不可用，直接进入安全模式。

## 八、Android 适配要点

- 插件文件放在应用私有目录，设为只读。Android 11 起不允许加载可写的 dex 或 jar。
- 类加载使用 `DexClassLoader`，优化目录按插件 id 与版本隔离。多版本并存时的 ART 行为未实测。
- Activity 与 Service 通过非导出的代理组件转发，路由带 generation 标记，旧版本组件在释放前继续可用。
- 同进程插件的崩溃会拖垮整个应用，因此可信档位插件必须经过审核，不能放任何不受控代码。
- 受限档位的进程隔离在 Android 上是本项目的主要技术风险。已知方向是一个插件一个进程，但内核不提供，需要单独做可行性验证。

## 九、内核门禁

- `third_party/cordis/` 固定在 `7b13e6b`，`KERNEL.lock` 记录上游 URL、提交哈希、目录树哈希、导入日期。
- 门禁只校验目录树哈希与 `KERNEL.lock` 一致。不做与基线提交的 diff，不依赖 SNAPSHOT。
- 任何对 vendor 目录的修改，只能先在上游分支完成，再手动同步，每次同步更新 `KERNEL.lock` 并经人工审核。
- 内核中不允许新增权限、信任、登记相关代码。门禁脚本需要包含这项检查（对 `core`、`loader` 搜索相关关键字，命中则失败）。

## 十、构建检查

- 依赖方向检查：按第二节列出的允许依赖，任何越界依赖使构建失败。
- 契约稳定性检查：`host-api` 的公开接口变化，必须同步升版本号，否则失败。
- 清单字段检查：清单规范的字段集合与 `host-core` 中的解析器字段集合一致，任何不一致失败。
- 内核门禁检查：见第九节。

## 十一、测试计划

**JVM 可测（`host-core`）**
- 清单解析与校验：清单规范第 15 节列出的全部用例。
- 状态机：第四节的每一条合法转换，以及至少一组非法转换，确认被拒绝。
- 依赖解析：缺失、版本不满足、循环依赖、可选依赖缺失各一组。
- 权限门：默认拒绝、授权后放行、撤销后拒绝。
- 失败计分：阈值前、阈值后、窗口滑出各一组。

**JVM 集成（`host-runtime` + `third_party/cordis`）**
- 内核 `core` 与 `loader` 的已有测试，作为第一步的基线。
- 插件卸载后副作用被撤销，LIFO 顺序正确。
- 依赖者先于提供者卸载。

**Android 真机（`host-android`）**
- 插件加载、卸载、依赖缺失拒绝。
- 替换失败回滚。
- 安全模式在异常退出后正确进入。
- Activity 和 Service 代理的路由与 generation 行为。

**未实测项（必须在对应阶段前验证）**
- 多版本 dex 在 ART 上的优化目录行为。
- Android 上受限档位的进程隔离可行性与成本。
- 事件分派对监听器异常的实际影响（目前只做了读码判断）。
- HMR 是否需要接线（目前不接线，只做替换事务）。

## 十二、实施顺序

1. 新仓库，vendor 内核，`KERNEL.lock`，JVM 跑通 `core`、`loader` 测试。
2. `host-api` 第一版：接口与数据类型，无实现。
3. `host-core`：清单解析与校验，先过清单规范的全部用例。
4. `host-core`：状态机与转换表，先过状态机用例。
5. `host-core`：依赖解析、权限门、失败计分。
6. `host-android`：安装、私有目录、类加载、代理组件。
7. `host-runtime` 与宿主骨架：入口页、插件管理页、安全模式，无插件时可工作。
8. 第一个插件：只验证加载、卸载、依赖缺失拒绝。
9. 之后才是功能插件、资源插件、集成插件，以及受限档位的进程隔离。

每一步完成后，停下来验证，通过了再进入下一步。

## 十四、app结构

1.新增一个 app/ 模块，Android application，它是唯一能产出 APK 的模块。
