# 新 EV 总规则（最终版）

## 一、方向

1. 新 EV 是一个新项目。旧 EV 归档为只读，不再在旧结构上修改。
2. 内核是上游 cordis-kotlin 的 `core` 和 `loader`，vendor 进仓库，固定在 `7b13e6b`，只通过上游补丁修改。
3. 宿主只做机制和裁决，不做能力。没有任何插件时也必须能独立工作。
4. 插件按四类划分：基础、功能、资源、集成。信任按来源分三档：可信、受限、不可信。
   类型按"做什么"切，档位按"来源"切，两者不混用。
5. 依赖指向接口并声明版本，宿主在装配时检查。

## 二、树形结构

```
整体
├── 内核 【vendor，冻结，只提供原语】
│   ├── 树与生命周期：插件注册、卸载时按 LIFO 撤销副作用
│   ├── 服务注入：服务名、依赖等待、提供者撤销时先等依赖者
│   ├── 装载：类加载隔离、整树事务、模块级替换与回滚
│   └── 不含：权限、信任、登记、产品逻辑
│
├── 宿主 【没有任何插件时也必须能独立工作】
│   │
│   ├── 入口 【不依赖机制里可能坏的部分】
│   │   ├── 引导（新用户）
│   │   └── 插件管理页（只展示和触发，不持有业务逻辑）
│   │
│   ├── 机制 【怎么让插件存在并运行，基于内核原语实现】
│   │   ├── 装配：这次启动加载哪些插件、什么顺序
│   │   ├── 生命周期：加载、停止、重启、dispose 级联
│   │   ├── 依赖解析：依赖指向接口，检查提供者存在且版本满足
│   │   ├── 循环依赖：装配阶段拒绝
│   │   ├── 替换：同一接口且版本满足才换，否则拒绝
│   │   ├── 隔离执行：按信任档位选执行环境（同进程 / 子进程或隔离容器）
│   │   └── 提供者不可用时的传播：停还是降级，只在这里决定
│   │
│   ├── 裁决 【谁能做什么，用户同不同意】
│   │   ├── 权限：宿主申请、记录、撤销，按清单统一开放给插件
│   │   ├── 信任判定：按来源和签名定档位，插件不能自己声明信任
│   │   │   ├── 可信：随包内置、签名通过 → 同进程
│   │   │   ├── 受限：用户确认安装的第三方 → 子进程，只经 broker 调用
│   │   │   └── 不可信：来源或签名不明 → 默认拒绝；判定缺失按不可信处理
│   │   ├── 启用、停用、卸载的许可
│   │   └── 数据去留的规则：规则归宿主，数据内容归插件
│   │
│   ├── 登记 【只查表，不理解内容】
│   │   ├── 服务：服务名 → 提供者（接口 + 版本）
│   │   ├── 页面：页面 id → 入口
│   │   └── 主题：插件 id + 主题 id，宿主不认识主题字段
│   │
│   └── 恢复 【假设已有东西坏了，只调用机制的接口】
│       ├── 失败计分：受限档位的插件崩溃或超时累计扣分，超阈值停用并阻止再注册
│       ├── 安全模式：只触发机制的停止，自己不实现停止
│       ├── 回滚：回到上一个可用版本
│       └── 崩溃记录：插件版本、激活状态、失败阶段
│
└── 插件 【宿主不理解它们的业务内容】
    │
    ├── 基础插件 【能力提供者，能力集合封闭】
    │   ├── 随包内置，默认启用，可被同接口的签名实现替换
    │   ├── 只做执行：存储、网络、日志
    │   └── 不做裁决，不管自己的生死
    │
    ├── 功能插件 【页面和行为】
    │   ├── 清单声明：依赖的接口、需要的权限、提供的服务、可降级项
    │   └── 可降级项只是名字，宿主记录状态并发出"已降级"信号
    │
    ├── 资源插件 【数据、主题、模型配置】
    │   ├── 叶子节点，不能依赖其他插件
    │   └── 需要的能力通过能力类型声明，由机制查表满足
    │
    ├── 集成插件 【对接外部系统】
    │   ├── 模型服务、云同步、第三方 API 等
    │   ├── 凭据由宿主保管和裁决，插件只拿到经授权的访问结果
    │   └── 按来源定档位，外部网络访问受裁决控制
    │
    └── 其他类 【待补充，目前未发现新类型】
```

## 三、内核、宿主、插件的关系

依赖方向单向：插件 → 契约包（host-api）→ 内核原语；宿主 → 内核原语和契约包。内核不依赖宿主，也不知道插件存在。

1. 插件只能依赖契约包。插件可用的内核类型，要么由契约包重新导出，要么经契约包的接口间接使用。插件不能直接依赖宿主私有包（host-runtime）。
2. 宿主是唯一的装配者。插件的加载、注册、卸载都由宿主通过内核原语完成，插件不能自己调用内核的装载接口。
3. 权限、信任、登记全部在宿主，内核里没有。内核只回答"能不能注册、能不能撤销"，不回答"能不能做"。
4. 停止靠内核的 LIFO 撤销。宿主的停止、重启、安全模式最终落到内核的 dispose 级联上，宿主不另写一套清理逻辑。
5. 隔离分两层。内核只提供同进程的失败隔离（单个插件失败不影响兄弟插件），其事件总线对监听器异常没有保护。宿主要自己包一层事件分派，并负责受限档位的子进程隔离。内核不做进程隔离。
6. 内核冻结，改动只走上游。宿主需要的功能，如果内核做不到，就在宿主里补，不改内核。

## 四、工程约束

1. 内核：vendor 到 `third_party/cordis/`，固定在 `7b13e6b`，保留上游 LICENSE 与 NOTICE。
   `KERNEL.lock` 记录上游 URL、提交哈希、目录树哈希、导入日期。门禁只校验目录树哈希与 `KERNEL.lock` 一致。
   不使用 SNAPSHOT 依赖，不再以某个基线提交做 diff（`88bae84` 在本仓库不存在）。
2. 内核改动只能先在上游分支完成，再手动同步回来，每次同步更新 `KERNEL.lock`，并需要人工审核。
3. 第一版只引入 `core` 和 `loader`。`include`、`hmr`、`packages`、`packager` 等需要时再加，每个都要写明理由。
4. 模块划分：`host-api`（契约，版本严格管理）、`host-runtime`（宿主私有，插件类路径不可见）、`plugins/*`（每个插件一个模块，按四类分放）。
5. 共享包列表只在一处定义，Android 与 JVM 共用。
6. 服务依赖统一走 `inject`，插件在清单中声明接口和版本，宿主装配时检查。描述符中的模块依赖只允许宿主声明，插件不能自行添加。
7. 构建顺序：
   - 第一步：新仓库、vendor 内核、`KERNEL.lock`，JVM 上跑通 `core` 和 `loader` 的测试。
   - 第二步：`host-api` 契约，只写接口，不写实现。
   - 第三步：宿主骨架，能启动、能进安全模式、能显示插件管理页，无插件时可工作。
   - 第四步：第一个插件，只验证"加载、卸载、依赖缺失时拒绝"。
   - 之后才是功能插件和隔离档位。子进程隔离不放进内核，单独实现。
8. 旧仓库打只读标签，并附说明：基线哈希不存在、门禁依赖不存在的提交、内核为 SNAPSHOT。
