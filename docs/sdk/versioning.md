# 契约版本门

> 宿主与插件之间"能不能一起工作"的唯一判定规则。
> 代码：`host-core/.../HostApiRange.kt`（解析与比较）、`PluginValidator.apiGate`（判定）。
> 宿主当前版本：`host-api/.../PluginContract.kt` 里的 `HOST_API_VERSION = "1.0.0"`。

## 1. 两条门，一次只走一条

| 容器声明了什么 | 走哪条门 | 判定 |
|---|---|---|
| `hostApi` 范围（如 `>=1.0.0 <2.0.0`） | **范围门** | 宿主版本是否落在范围内 |
| 没声明 `hostApi` | **整数门**（实验期遗留） | `apiVersion == 1` 才过 |

**两条门不会同时生效。** 声明了范围，整数门完全退出——否则"到底哪个拒了我"只能靠读源码。
这条规则有测试守着：`声明了范围就不再走整数门`（`PluginValidatorApiGateTest`）。

## 2. 范围语法

以空格分隔的比较符合取，**全部满足**才算命中：

| 写法 | 含义 |
|---|---|
| `>=1.0.0` | 大于等于 |
| `>1.0.0` | 大于 |
| `<=1.0.0` | 小于等于 |
| `<1.0.0` | 小于 |
| `=1.0.0` | 精确等于 |
| `1.0.0` | 与 `=1.0.0` 相同 |

版本号必须是**严格三段数字**：`1.0`、`v1.0.0`、`1.0.0-rc1` 都不接受。

### 故意不支持的写法

`^1.0.0`、`~1.2.3`、`1.x`、`*`、`>=1.0.0 || >=3.0.0` —— **解析失败即拒绝**。

理由很直接：一个把 `^1.0.0` 当 `>=1.0.0` 理解的解析器，会让插件作者以为自己声明的
上界生效了，而它没有。明确拒绝至少让人当场知道要改。

要写"1.x"就用 `>=1.0.0 <2.0.0`，两者本来等价。

## 3. 拒绝码

| 码 | 含义 | 作者该做什么 |
|---|---|---|
| `API_RANGE_INVALID` | `hostApi` 写了我读不懂的东西 | 改成第 2 节的语法 |
| `API_VERSION_MISMATCH` | 范围合法，但宿主不在里面；或旧容器整数门没过 | 换宿主版本，或升级容器 |

两个码分开是有意的：一个的处理是**改声明**，另一个是**换包**。混成一个码，作者只能在
两个完全不同的修法之间猜。

## 4. 怎么声明

**jar（sidecar `.json`）**

```json
{
  "id": "ev.buan.plugin.ping",
  "version": "1.0.0",
  "entryClass": "ev.buan.plugin.ping.PingPlugin",
  "hostApi": ">=1.0.0 <2.0.0",
  "apiVersion": 1
}
```

**apk（manifest meta-data）**

```xml
<meta-data android:name="cordis.hostApi" android:value="&gt;=1.0.0 &lt;2.0.0" />
```

> XML 里 `<` 与 `>` 必须转义成 `&lt;` / `&gt;`，否则 manifest 直接编译失败。
> 这行很容易漏，`ev-manifest-spec.md` 里有同样提醒。

## 5. 什么时候升版本

| 变更 | 宿主版本 | 老插件还能跑吗 |
|---|---|---|
| 加字段（有默认值）、加服务、加权限位 | `1.0.0 → 1.1.0` | ✅ 能（声明 `>=1.0.0 <2.0.0` 的都在范围内） |
| 改语义、删字段、改枚举含义 | `1.x → 2.0.0` | ❌ 不能，必须重编 |
| 只改文档、注释 | 不动 | — |

**判断标准只有一条**：老插件按原来的理解继续跑，会不会做出错误的事情？
会，就是 major；不会，就是 minor。

## 6. 改这个门的流程

1. 改 `HostApiRange.kt` 或 `apiGate`
2. 改本文件
3. 跑 `:host-core:test`
4. 在提交信息里写明"哪类插件会因此被拒"

## 7. 与 `ev-manifest-spec.md` 的关系

规范里早就写了 `hostApi` 字段，但**在本次改动之前没有任何代码读它**——
规范与实现漂移了整整一个实验期。现在两者一致：规范管格式，本文件管判定。
