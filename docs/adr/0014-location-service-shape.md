# ADR-0014：定位服务——一个方法、精度优先、时间必须跟着走

- 状态：已采纳
- 日期：2026-11-10
- 相关：[ADR-0013 只读个人数据服务](0013-read-only-personal-data-services.md)、
  [docs/sdk/host-services.md](../sdk/host-services.md)

## 背景

位置和前面三个只读服务不同：它可能**实时变化**，而且"读缓存"与"主动定位"的代价差一个数量级
（前者零成本，后者唤醒无线电、耗电、可能超时）。

第一版设计是照惯例给两个方法：`lastKnown()` 和 `current()`。被否决了，理由见 D1。

## 决策

### D1：只有一个 `locate(maxAgeMs, maxAccuracyMeters, timeoutMs)`

`lastKnown` 与 `current` 不是两个功能，而是同一条轴的两端：**愿不愿意花电**。

拆成两个方法，这个选择就甩给了调用方——也就是模型。而模型在调用前根本不知道缓存有多旧，
只能先调 `lastKnown`、看一眼 `ageMs`、再决定要不要 `current`。多一次往返、多一个选错的可能。

合成一个方法后，`timeoutMs = 0` 就是"只读缓存"，没有第二个方法。

### D2：精度是硬门槛，新鲜度是门槛内的偏好

这是整个设计里最容易写错的一条：**新的不一定更好**。

室内刚拿到的 network 定位可能是 2000 米精度，而五分钟前的 GPS 定位是 8 米。
按"新的赢"，调用方会得到一个看起来新、实际没用的坐标，然后自信地报出一个错误的区。

规则：

1. 有满足精度门槛的候选 → 取其中**最新**的
2. 一条都不满足 → 取**精度最好**的（一条 8 米的旧定位仍比 2000 米的新定位有用）

### D3：两个时间戳，`ageMs` 必须用单调时钟

- `capturedAtEpochMs` 是墙钟，说给人听（"三分钟前"）
- `ageMs` 由 `elapsedRealtimeNanos` 算，用户改时区、系统对过 NTP 都不会让它变成负数

只信墙钟的差，会在时钟被校正的那一刻得出荒唐的年龄。

### D4：请求失败返回旧缓存，不返回 null

返回 null 会让模型说"我拿不到位置"；而一条标着"已过期 47 分钟"的坐标仍能让它给出有用的话。
沉默比不准更糟——前提是过期信息必须跟着结果一起走，由调用方自己判断。

### D5：权限降级如实反映，`isMock` 必须暴露

只给了模糊定位时请求 `gps` 会直接抛。宿主先判断授到哪一级，走 `network`，
然后如实报一个大精度值——而不是假装失败，也不是假装很准。

`isMock` 同理：模拟定位能让 agent 得出任何结论，隐藏它等于给了一个可信的错误答案。

### D6：合并规则放 `host-core`，做成纯函数

`LocationPicker` 不认识 Android 的 `Location`（泛型 + 取值函数），因此可以在 JVM 上
一条条断言"新而糊输给旧而准"这类分支——这些分支在真机上几乎无法稳定复现。

## 代价与限制

- **没有持续监听**。要"每 5 分钟记一次轨迹"这种需求，这个接口做不了；
  那是另一条产品线，且要处理前台服务与耗电，不该混进一次性的 `locate`。
- **超时上限 30 秒**（实现里夹住）。调用方传更大的值也不会等更久。
- **精度数字在室内不可靠**。`accuracyMeters` 是系统自报的信心值，不是真值误差；
  一条 20 米的 network 定位在城市峡谷里可能差出几百米。
- **没有反向地理编码**。"我在哪"只给坐标，转成"国贸"要另一次网络请求，
  属于插件层的事，宿主不代劳。
- **`passive` provider 的缓存可能极旧**。它只会在别的应用请求定位时顺带记录，
  所以它常常是"最后一条"而不是"最新一条"——`ageMs` 会暴露这一点。
