# ADR-0001：原地演进，不开新仓

- 状态：已接受
- 日期：2026-11-06
- 相关：`docs/newdocs/最高规则/ev-final-rules.md`、`scripts/check.sh`

## 背景

仓库现在 383 个 Kotlin 文件 / 56,441 行，20 个插件、24 个构建模块。乱的形态很清楚：

- **枢纽类**：`HostRuntime` 1050 行同时做装配、服务发布、路由、主题、插件运维、安全模式；
  `AgentBrainService` 1036 行同时做循环、工具调度、审批、日志；
- **14 个主代码文件超过 400 行**，覆盖了宿主、业务、界面三层；
- **没有一条机器校验**：唯一的 tag 是 `boot-anim-v3-final`，`TODO`/`FIXME` 为 0——
  债务不在代码里留痕，只存在记忆和交接文档里，而且文档已经过期过一次。

“最高规则”原文写的是：新 EV 是一个新项目，旧 EV 归档为只读，不再在旧结构上修改。

## 决策

**在原地演进，不开新仓。**

理由三条：

1. 换仓库买不到边界。新仓前三个月更干净，但如果仍然没有门禁，同一个位置会长出同一个枢纽类。
   决定腐烂速度的是“边界能不能被机器校验”，不是仓库地址。
2. 现有仓库有重构唯一的资本：**能在真机上跑**。构建链、20 个插件、单测、部署脚本都在。
   新仓要么重写，要么把同样的代码搬一遍——搬家本身不产生边界。
3. 归档会造成两边漂移。旧仓只读、新仓开发，任何一次“这个 bug 只在旧仓能复现”都要跨仓处理。

## 后果

- “最高规则”§一.1 与 §四.8 同步改写；规则与代码冲突时以规则为准，改规则先写 ADR。
- 每一步都必须保持主分支可构建、可装机；不允许出现“这段时间编译不过”。
- 第一章的门禁先行：内核哈希、模块边界、文件行数（`scripts/check.sh`）。
  门禁先红后绿，红名单就是待办清单。

## 阶段（详见对话中的六阶段计划）

0. 立规矩：tag、规则改写、三条门禁、本 ADR —— **本 ADR 所在阶段**
1. 契约收口：`plugin-api` → `host-api`，插件不再依赖宿主
2. 宿主拆分：`host` → `host-app` + `host-runtime`，`HostRuntime` 拆成四个类
3. 插件归位：按基础/功能/资源/集成四类归位，同时做减法
4. 拆业务枢纽：`AgentBrainService`、`MemoryPage`、`EvModelProvidersScreen`、`BrowserWebView`
5. 运行时治理：执行预算（dispatcher、并发准入、强制寿命、内存水位）；隔离档位单独一个里程碑

## 被否决的方案

- **开新仓重写**：验证成本从“改一处跑一次”变成“全跑一次”，且六个月后同样需要门禁。
- **一次大提交整理**：中途不可验证，回滚粒度等于零；与“必须随时可装机”直接冲突。
- **只写文档定边界**：本项目已经证明没有机器校验的约定会漂移——交接文档把“问题”和“已修”混写过。
