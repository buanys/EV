# ADR-0007：审批拆成"策略"与"人工"两层，工具前缀硬规则

- 状态：已采纳
- 日期：2026-11-05

## 背景

高危工具的执行前只有一道关：`ApprovalService.request`。它的唯一实现（`ApprovalGate`）
住在 `ev-ui` 里，于是**没有 UI 就没有审批腿**——任何 headless、远程、后台形态都只能对
所有高危工具 fail-closed。fail-closed 本身的纪律是对的（三处拦截都有测试），
问题在位置：把"判断"和"展示"绑在了一起。

同时，`executeGuarded` 里除了审批没有任何可插拔的检查点。想加一条"这个路径不在工作区
就不许写"的规则，只能改 brain——而 brain 不该知道路径白名单这种东西。

## 决策

### 1. `ApprovalPolicy`：把预判从展示里拆出来

新契约（`agent-api`），brain 在问人之前先问它。三种判定：

- `ALLOW`：明确安全，不问人（**唯一会跳过人类的一档**）
- `DENY`：明确禁止，不问人
- `ASK`：仍需人类决定

没有 policy 时一律 `ASK`，行为与它出现之前**完全一致**。policy 只能把 `ASK` 变成
`ALLOW` 或 `DENY`，不能绕过下面的 guard。

坏掉的 policy 按拒绝处理——一个抛异常的插件不能变成放行。

### 2. `ToolGuardRegistry`：单调的硬规则

新契约（`agent-api`），由 brain 自己发布，其它插件 `lookup` 后 `register`，
卸载时调用返回的撤销函数。

**只能拒绝或弃权，不能改参数、不能重排顺序。** 这是从 DSH 的 monotonic guards 借来的
唯一一条规矩：如果后注册的 guard 能被先注册的绕过，安全强度就取决于插件安装顺序，
而安装顺序是用户随手点出来的。所以注册表不排序、不合并、不提供"覆盖"。

### 3. 执行顺序

```
guard（硬规则，绕不过）
  → policy（预判，只能缩放"要不要问人"）
    → approval（问人，挂起直到回答）
      → 工具本体
```

guard 放在审批之前，因为"先问人再被规则否决"会让用户白做一次决定。

### 4. 为什么 policy 现在没有默认实现

因为**错误的 `ALLOW` 是最危险的一类改动**，而"哪些参数组合是安全的"需要产品判断，
不是接口设计能解决的。本次交付的是机制：接口 + brain 消费 + 空实现安全回退。
后续要落地，应该在真正了解工具语义的地方提供一个保守实现（例如 `agent-shell`
对 `rm -rf` / `mkfs` / 写入块设备这类明确灾难性命令返回 `DENY`），
而不是在 brain 里堆一份它不该拥有的黑名单。

## 后果

- headless 形态可以通过装一个 policy 插件获得安全腿，不再被"必须有 UI"卡死。
- 不装 policy 的机器行为零变化，包括所有现有测试。
- guard 是热路径上的内存遍历（每次工具调用一次），没有 I/O。
- `BrainCapabilities` 多了 `sessionLog` 与 `policy` 两个可空字段，全部按"缺失即降级"处理，
  与既有哲学一致。

## 不做

- **不把 `ApprovalGate` 从 `ev-ui` 搬走**：它管的队列、session allow、对话框仍然属于展示层，
  搬走会牵动 6 个既有测试而换不来新能力。真正的解耦由 `ApprovalPolicy` 完成——
  判断可以离开 UI，提问不必。
