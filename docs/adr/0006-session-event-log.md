# ADR-0006：会话事件流是历史的唯一真相源

- 状态：已采纳
- 日期：2026-11-05

## 背景

在本次改动之前，一次对话的历史只有一个存放处：`agent-memory` 发布的 `MemoryService`。
`AgentBrainService` 在每一轮里把 user / assistant / tool / 图片说明 / 运行时提示这几类消息
依次 `append` 进去，下一轮再 `history()` 读回来。这条路能跑，但有三件事做不到：

1. **崩溃恢复**：进程被杀在工具执行中间时，没有任何记录能说明"这一轮停在哪"。
2. **回放**：想知道模型当时到底看到了什么，只能反推 `HistoryTrim` 的裁剪规则。
3. **轨迹**：`agent-log` 有一条设计得相当严格的 append-only 审计流（seq 严格 +1、不可改写、
   `sys.void` 纠正、`sys.gap` 补缺口、坏行隔离），但它的注释自己写着"不接 agent"——
   两条流各自成立，中间没有桥。

结果是：**审计骨架挂在一条没有 agent 的链路上，真实对话跑在一个不受审计的循环里。**

## 决策

新增 `SessionLog`（`agent-api`），由 `agent-log` 实现，`agent-brain` 消费。

1. **契约放在 `agent-api`**，因为插件之间不能编译依赖。`agent-log` 对着 agent-api 的
   classes.jar 编译，sidecar 声明 `dependencies: ["ev.buan.plugins.agent.api"]`。
2. **写入顺序：先日志，后 memory。** 反过来的话，日志写失败会留下"非空但断了一截"的流，
   下一次读历史会采用不完整的那份，用户看到对话丢了一段。先写日志的最坏情况是 memory
   少一条（蒸馏输入旧一点），对话本身不受影响。
3. **读取顺序：日志非空则用日志，否则退回 memory。** 不做合并——合并要定义去重与顺序，
   而这两份数据本来就该是同一串消息。退回 memory 让升级前的老会话仍然有历史，
   不需要迁移脚本。
4. **按会话分片**：`sessions/<sha256(sessionId)[:16]>.jsonl`。全局审计流是跨会话连续的，
   会话流按会话分片——清空一个会话不该在别的会话里留下一个洞。文件名哈希掉，因为
   sessionId 来自 UI，直接拼路径等于把路径穿越交给调用方。
5. **事件类型只有两种**：`Message` 与 `TurnEnded`。`AgentMessage` 已经能表达角色、内容、
   工具调用和结果关联；按"用户说了什么 / 模型说了什么 / 工具返回了什么"拆成十种事件，
   投影时还得再写一遍同样的分派，多出来的只有漂移的机会。
6. **图片不落盘**：`AgentMessage.images` 是 1 MB 级的 transient 数据，模型随时可以重读，
   塞进每轮事件一天就吃光配额。重建出来的消息只保留说明文字，与 memory 的取舍一致。

## 后果

- `sessions/` 会占用 `PLUGIN_STORAGE` 配额（宿主 20 MB），需要留意。目前每条事件都触发
  `EventLog` 的全文重写，单会话几百条事件、几百 KB 量级，写入是毫秒级；真正的优化
  （追加写 + 快照分段）等有量再说，现在加只会多一个半吊子的写入路径。
- `MemoryService` 从"权威"降为"派生物"。它的蒸馏、笔记、索引不受影响，但不再定义
  "历史是什么"。将来可以把 `history()` 改成从 `SessionLog` 投影，本次不做。
- 清空会话时两个存储都要清。目前 ev-ui 没有清空持久化历史的入口（新建会话即新
  sessionId），所以暂不存在不一致；一旦加"删除对话"，必须同时调 `SessionLog.clear`。

## 不做

- **不重建完整请求**：system prompt 每轮重新组装，不落盘（与现状一致）。DSH 会把
  `request/header` 记进日志以便精确重放，对 EV 来说这会让日志体积与"提示词改了怎么办"
  的问题同时变复杂，收益不成比例。
- **不做 fork**：事件流已经具备条件（切点 + 继承标记），但没有产品入口，先不做。
- **不做迁移**：老会话靠"退回 memory"继续工作，不自动回填日志。回填一旦中途失败，
  会留下半份日志，反而破坏"非空即可信"的前提。
