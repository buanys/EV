# ADR-0009：信任三档的判定，与"受限档同进程"这笔欠账

- 状态：**已采纳**（判定、门禁、子进程 broker 全部落地；2026-11-06 修订过一次判定依据）
- 日期：2026-11-06
- 关联：ADR-0003（权限不是沙箱）、ADR-0008（未签名插件的信任）

## 背景

最高规则 §二 要求信任判定分三档，并且**档位决定执行环境**：

```
可信：随包内置、签名通过      → 同进程
受限：用户确认安装的第三方    → 子进程，只经 broker 调用
不可信：来源或签名不明        → 默认拒绝
```

实现前，仓库里只有两态：**签名 / 未签名**。`PluginTrust` 只报告签名事实，
`PluginValidator` 要么放行要么拒绝，两者的结果对运行时没有任何影响——
所有插件同进程、同 UID、都能调 `su`。也就是说：**"档位"这个概念在代码里不存在**，
界面上也只有一个"未签名"标签，用户看不出自己在承担什么。

## 决策一：档位由三个事实决定，判定是一个纯函数

`host-core` 新增 `TrustGate.decide(origin, signing, sha256, approvedSha256, hostCertificateSha256)`。
输入全部是宿主测得的事实，**没有一条来自插件的自述**。优先级就是判定的顺序：

| 事实 | 档位 | 理由写进卡片 |
|---|---|---|
| 来源 = 内置（assets） | **可信** | 内容由宿主 APK 的签名担保 |
| 外部 + 签名与宿主一致 | **可信** | 我们自己的构建产物 |
| 外部 + 已批准这批字节（sha256 相等） | **受限** | 用户确认过的第三方容器 |
| 外部 + 未签名 + 未批准 | **不可信** | 待确认 → 走批准流程 |
| 外部 + 第三方签名 | **不可信** | 签名与宿主不一致，拒绝 |
| 签名证书集为空 | **不可信** | 签坏了，批准也不放行 |

两个刻意的选择：

1. **内置压过签名**。jar / dex 装不下 Android 签名，如果坚持"内置也要签名通过"，
   随包内置的 jar 会落到"未签名待确认"——正式版首次启动要用户逐个确认自己的插件。
   而 assets 里的容器改一个字节 APK 签名就已失效，再验一次容器签名只是把同一件事做两遍。
2. **批准按字节，不按 id**。批准的是"这批字节"，换了字节就不再是同一个东西。
   （这条与 ADR-0008 的能力面自动通过并存：能力面管"要不要再问一次人"，
   这里管"问了之后的档位是什么"。）

`ValidationResult.Accepted` 现在**带着** `TrustDecision` 一起返回，`InstalledPlugin.trust`
把它带过安装期，激活门和卡片读的是同一个值——不存在"装的时候算一次、跑的时候算另一次"。

## 决策二：门禁放在激活门，不在安装门

不可信的容器装不进来（validator 拒绝），**但"装进来"与"允许执行"是两件事**：
权限门就在这两者之间（`PERMISSION_DENIED` 时仍然 publish，让用户去授权）。
信任门同理放在 `HostActivation.activate`，与安全模式、失败计分、权限门并列：

| 档位 | 未实现隔离时 |
|---|---|
| 可信 | 同进程运行 |
| 受限 | **调试包**同进程运行；**正式包不执行**，卡片写明"需要子进程隔离，本版尚未实现" |
| 不可信 | 永不执行 |

调试包放开的理由：可调试包本身的信任已经归零（谁都能 attach 进去改代码），
隔离插件换不来任何安全性，而每改一行代码都要重新确认插件会让开发瘫痪。
这与 `autoTrustUnsigned` 绑在 `FLAG_DEBUGGABLE` 上的是同一个判断，所以它们共用 `allowsRestrictedInProcess`。

结论：**正式包对受限档位是 fail-closed 的**。今天设备上的 17 个插件全是未签名 jar，
在调试包里按"受限 + 放行"运行，卡片上第一次如实写出"受限"。

## 决策三：受限档怎么进子进程（实现后修订）

**谁进子进程，由插件声明，不由宿主推断。** sidecar（或 APK 元数据）写：

```json
{ "isolation": "separate-process" }
```

再叠加三条机械约束（`RestrictedProfile`）：只能声明 `NETWORK` / `PLUGIN_STORAGE`、不能有桌面
入口、不能有插件依赖。四条都满足才进子进程。

为什么不是推断——**第一版就是推断，真机当场失败**：只按权限和依赖判，`agent-brain`、`ev-ui`
等 12 个插件都显得"可隔离"（它们 sidecar 里的 `dependencies` 是空的，靠 `ServiceDirectory`
在运行时查服务），于是全部被塞进子进程，然后在子进程里因为拿不到宿主服务而集体失败，
工具数从 45 掉到 33。宿主**看不出**插件经由服务目录查了谁，所以这件事只能由插件自己声明。

broker 的接口粒度按上一版就定好的来：

- **只代理 `ToolRegistry`**：`specs` / `invoke`，字符串与字节进出，跨 Binder 无痛；
- **不做双向代理**：子进程里没有凭据、没有宿主服务，声明了别的权限就进不去；
- **同一 APK 的子进程不是安全边界**：同 UID、同签名、同 SELinux 域，它换来的是**故障隔离与
  生命周期独立**（崩溃、超时、可单独回收），不是权限隔离。而"真正的权限隔离"在插件模型里
  **不存在**：跨 UID 就是跨应用，论证见 [ADR-0003](0003-permission-scope.md) 的「为什么"换一个 UID"
  这条路也堵死」——加载必须在宿主进程里发生，类身份过不去，`isolatedProcess` 又是空壳。

协议是手写的 `Binder.transact`（三个 code：LOAD / INVOKE / UNLOAD），不用 AIDL：参数全是
字符串与整数，AIDL 只会在中间加一层 codegen。子进程侧 `ChildPluginRuntime` 只提供四个东西——
`ServiceDirectory`（里面只挂 `ToolRegistry`）、`PermissionService`（读宿主写的同一份授权）、
`ToolRegistry`、按需的 `PluginStorage`——其余一律没有。

## 验证（2026-11-06，真机）

固定装置：`tools/probe-remote`（`-PevTestPlugins` 才进构建），一个只会回答自己 pid 的工具。

| 检查 | 结果 |
|---|---|
| 装进子进程 | 日志 `plugin isolated … · 1 个工具在子进程`，进程列表出现 `ev.buan:plugin` |
| 工具注册到宿主 | 首页 45 → **46 个工具** |
| 调用跨进程 | `remote_ping` 返回 `pong pid=19583`，宿主进程是 19078 |
| 子进程被杀 | 主线程日志 `plugin … 的子进程退出：工具已撤下`，工具从总线上撤下 |
| 重启后恢复 | 重新隔离，新的 `:plugin` 进程，工具回到 46 |
| 撤掉固定装置 | 回到 17 个 accepted / 45 个工具，无 `:plugin` 进程 |

## 影响

- `PluginCandidate.origin` / `verifyAtLoad(origin=…)` 默认 `EXTERNAL`——默认值取少信任的一侧。
- 卡片：一眼层显示 `· 可信`（常态，不显示）/ `· 受限` / `· 不可信`；展开区有一节"信任"，
  写档位、理由与"这一档在运行时意味着什么"。
- 新增 9 个 `TrustGate` 单测 + 4 个 validator 用例；`Accepted` 改成带字段后 12 处断言改为 `is Accepted`。

## 没做的（诚实清单）

1. **只支持工具类插件**：声明了 `SECRETS`、桌面入口或插件依赖的受限插件进不了子进程；
   正式包里它们不执行，调试包里按"同进程降级"运行。
2. **子进程里的插件仍然能 `su`**：同 UID 同权限，隔离的是"宿主服务"和"崩溃范围"，不是能力。
3. **没有超时保护**：`invoke` 会一直等子进程；工具卡死目前只能靠用户停用插件。
4. **调用结果没有大小上限**：图片以 base64 走 Parcel，超大结果可能触发 binder 事务上限
   （1 MB 左右），还没实测。
